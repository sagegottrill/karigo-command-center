# FleetOpsX — Routes, Portals and How a Role Travels End to End

Everything below is read from the code as it stands. File paths are relative to the
repo root; every route file lives in `src/routes/` and every route is generated into
`src/routeTree.gen.ts` (regenerated by the TanStack Start plugin — do not hand-edit it).

---

## 1. The shape of the whole thing

```
Browser request
  │
  ├─ __root.tsx            hostname → TENANT (slug, name, logo, icons)          [public]
  │
  ├─ /                     landing / marketing                                  [public]
  ├─ /privacy, /deleteaccount                                                   [public]
  │
  ├─ /superadmin/*         platform owner console (its own login + its own token)
  │
  └─ /workspace            WorkspaceLayout (a plain boundary, no auth logic)
       │
       ├─ /workspace/login                  internal sign-in                     [public]
       ├─ /workspace/account-type           "Internal or Partner?" chooser       [public]
       ├─ /workspace/forgot-password        first-login / reset password
       │
       ├─ /workspace/app                    ★ THE STAFF PORTAL SHELL (guard here)
       │     └─ AppShell → role picks SIDEBAR + HEADER
       │        └─ every department page (its own beforeLoad guard)
       │
       └─ /workspace/customer-portal        partner portal
             ├─ /login                       [public]
             └─ /_auth  (guard: partner role) → /dashboard, /request, /:requestId, /notifications
```

The one rule that explains most of the code: **a guard never trusts the client for
access; it only decides what the person sees.** The JWT (issued by the API) is the
real boundary. `beforeLoad` guards exist so a department never even renders another
department's chrome.

## 2. Where a session lives (the only keys that matter)

`src/lib/fleetopsx/apiClient.ts`

| localStorage key            | Written by                    | Read by                     |
| --------------------------- | ----------------------------- | --------------------------- |
| `fleetopsx_token`           | `authService.login`           | every `fetchApi` call       |
| `fleetopsx_user`            | `authService.login`           | `authService.getCurrentUser` |
| `fleetopsx_user_id`         | `authService.login`           | `authService.isAuthenticated` |
| `fleetopsx_roles`           | `authService.login` / `setRoles` | `authService.getRoles`   |
| `fleetopsx_user_name`       | `authService.login`           | header / avatars            |
| `fleetopsx_active_role`     | `setActiveRole` (header switch) | `getActiveRole`           |

API base: `VITE_API_URL` if set, else **same-origin `/api`** in the browser (Vite proxy /
Vercel rewrite) and `BACKEND_API_ORIGIN` (`http://2.28.45.216/api`) during SSR.

Every request sends `Authorization: Bearer <fleetopsx_token>`. A **401 on a request that
carried a token** clears the session and hard-navigates to `/workspace/login?next=…`;
badge/poll calls pass `{ softAuth: true }` so a background poll cannot log a user out.

## 3. Sign-in, end to end (internal)

`src/routes/workspace.login.tsx` → `src/lib/fleetopsx/services.ts` (`authService`)

1. The form optionally takes a **department** (`ADMIN_DEPARTMENTS` label, e.g.
   "Fleet Operations"). It is sent to the server (`POST /auth/login {username, password,
   department}`) — with a shared username the department decides *which account* the
   credentials open.
2. `authService.login` stores token + user + roles (all five keys above).
3. The chosen department is validated against the roles the account **actually holds**
   (`roleForDepartment(department, roles)` in `admin-departments.ts`). Not assigned →
   error toast, no session entered.
4. Redirect, in this order:
   - department chosen → `enterAuthenticatedApp(getRoleHome(chosenRole))`
   - **several roles** → a picker screen ("choose which department to open", `selectedRole`)
   - one role → `enterAuthenticatedApp(getRoleHome(onlyRole))`
5. `enterAuthenticatedApp` uses `window.location.replace`, so Back cannot return to the
   login form, and `installSessionGuards()` (session.ts) re-checks on `pageshow`/`focus`
   so a bfcache restore of a logged-out shell is bounced to `/workspace/login`.

Logout (`hardLogout`, header menu): `authService.logout()` → clears the token/user/roles,
clears `fleetopsx_active_role`, `window.location.replace("/workspace/login")`.

## 4. The role model

Roles are plain strings issued by the API. Three layers read them:

**(a) Canonical + alias RoleKeys** — `src/lib/fleetopsx/admin-departments.ts`

| Figma department label   | RoleKey(s) that grant it                                  |
| ------------------------ | --------------------------------------------------------- |
| Transport Admin          | `Transport Manager`, `Platform Admin`                     |
| Fleet Operations         | `Fleet Operations`, `Fuel Management`, `Fuel Manager`     |
| Tracking Operations      | `Tracking`, `Tracking Operations`                         |
| Loading Operations       | `Loading`, `Loading Operations`                           |
| Lubricant                | `Lubricant`, `Lubricant Manager`, `Lubricant Operations`, `Fuel Manager` |
| Fuel Management          | `Fleet Operations`, `Fuel Manager`, `Lubricant`           |
| Engineering and Maintenance | `Engineering`                                          |
| Parts and Store          | `Parts & Store`, `Parts and Store`                        |
| Accounts                 | `Accounts`, `Accountant`                                  |
| HR and Personnel         | `HR`, `HR & Personnel`, `HR and Personnel`                |
| Security                 | `Security`, `Gate Security`, `Gate`                       |
| Drivers                  | `Driver`                                                  |

**(b) Department-owned role groups** (shared by every page of that department)

- `HR_OWNER_ROLES` / `HR_ACCESS_ROLES` — `src/lib/fleetopsx/hr-helpers.ts`
  (owners: `HR`, `HR & Personnel`, `HR and Personnel`, `Transport Manager`,
  `Platform Admin`; access adds `Fleet Operations`).
- `ENGINEERING_OWNER_ROLES` / `ENGINEERING_ACCESS_ROLES` — `engineering-helpers.ts`
  (owners: `Engineering`, `Engineering & Maintenance`, `Engineering and Maintenance`,
  `Platform Admin`; access adds `Transport Manager`).

**(c) Capability gates — "may I do this", separate from "may I open it"**
`src/lib/fleetopsx/active-role.ts`

| helper              | true for                                              | used by                              |
| ------------------- | ----------------------------------------------------- | ------------------------------------ |
| `canSeeTmPricing`   | `Transport Manager`, `Platform Admin`, `Accounts`, `Accountant` | fuel-rate money, grand totals |
| `canLogTracking`    | `Tracking`, `Platform Admin`                          | Log New Location form                |
| `canLogLoading`     | the above + `Loading`, `Loading Operations`            | "Mark as Loaded"                     |
| `loggableLegs`      | Tracking → all stages; Loading → `Loading` only        | stage picker                         |
| `canViewLoading`    | Loading, Tracking, TM, PA, FO                          | loading board visibility             |

**(d) The active department (one person, several roles)**
`getActiveRole(roles)` reads `fleetopsx_active_role` and falls back to `roles[0]`. The
header's department switch calls `setActiveRole(role)` then dispatches
`window.fleetopsx:role-switched`; `AppShell` listens and re-picks the sidebar/header chrome
(the header is remounted with `key={activeRole}`). Switching department **never grants a
role the account does not hold** — it only chooses which assigned one is shown.

## 6. The staff portal shell — how the sidebar and header are chosen

`src/routes/workspace.app.tsx` (`AppShell`). Precedence is a single `if/else` chain, and
**the department shells win over the department-agnostic ones**:

```
departmentShell (hr | engineering | accounts | parts | inventory)   ← DepartmentSidebar
  → useGateShell        (Security)                                  ← GateSecuritySidebar
  → useLoadingShell     (Loading*)                                  ← LoadingOperationsSidebar
  → useLubricantShell   (Lubricant/Fuel Manager)                    ← LubricantSidebar
  → useTrackingShell    (Tracking*)                                 ← TrackingOperationsSidebar
  → useFoShell          (Fleet Operations, and NOT Transport Manager) ← FleetOperationsSidebar
  → otherwise                                                       ← TransportAdminSidebar  (TM / Platform Admin / anything else)
```

Every `shouldUse…Shell(roles)` predicate lives next to its sidebar, and they all repeat the
same exclusions (TM/Platform Admin never ride a department shell, FO never rides another
department's, tracking/security/loading/lubricant are mutually exclusive). Predicates are
evaluated against the **active role only** when the user holds several
(`active && roles.length > 1 ? [active] : roles`).

Sidebar contents per portal (labels → routes):

- **Transport Admin (TM / PA)** — Central Dashboard `/workspace/app`, New Request
  `/new-request`; PARTNER Account: New Account `/add-partner`, Account Management
  `/manage-partner`, Partner Requests `/partner-requests`; INTERNAL Account: New Account
  `/add-account`, Account Management `/manage-account`, Password Request
  `/password-request`; DEPARTMENTS: Fleet Operation `/fleet`, Manage Fleet
  `/fleet-registry`, Tracking Operations `/active-dispatch`, Live Tracking
  `/live-tracking`, Gate Security `/gate`, HR & Personnel `/hr`, Engineering
  `/engineering`, Parts & Inventory `/parts`, Fuel Pricing `/fuel-pricing`, Lubricant
  `/lubricant`, Accounts `/accounts`; Notification `/notifications`, Messages `/messages`.
- **Fleet Operations** — Fleet Dispatch `/dispatch`, Manage Fleet `/fleet-registry`,
  Dispatch History `/dispatch-history`, Tracking Operations `/active-dispatch`,
  Live Tracking `/live-tracking`, Lubricant `/lubricant`, Notifications, Messages.
- **Tracking Operations** — Tracking Operations `/active-dispatch`, Live Tracking,
  Notifications, Messages.
- **Loading Operations** — Loading Board `/active-dispatch`, Live Tracking, Notifications,
  Messages.
- **Gate Security** — Security Log `/gate`, Notifications, Messages.
- **Lubricant** — Disburse Request `/lubricant-disbursal` (first in the sidebar),
  Lubricant Inventory `/lubricant-inventory`, Disbursal History `/lubricant-history`,
  Notifications `/lubricant-notifications`.
- **HR** — Staff Record `/hr`, Notifications.
- **Engineering** — Work Orders `/engineering`, Truck Availability `/truck-availability`,
  Repair Spend `/repair-spend`, Notifications, Messages.
- **Accounts** — Dispatch Disbursal `/disbursal`, Disbursal Voucher `/disbursal-voucher`,

- **Inventory (storehouse)** — Inventory Desk `/inventory-desk`, Parts & Store `/parts`,

## 7. The `/workspace/app` guard (the gate every staff page sits behind)

`workspace.app.tsx` → `beforeLoad` (skipped during SSR, `typeof window === "undefined"`):

1. Profile + live token required. A stored profile with **no token** clears the session and
   redirects to `/workspace/login` (unless `VITE_USE_MOCK === "true"`).
2. `user.passwordResetRequired` → `/workspace/forgot-password`.
3. **Partner-only session** (`partnerOnly(roles, active)` — holds the partner role and it is
   the only one, or the selected one) → `/workspace/customer-portal/dashboard`.
4. `/workspace/app` exactly → `getActiveRoleHome(...)`; redirects to the active role's own
   home when that is not the Central Dashboard.
5. Unknown sub-path → `notFoundComponent: PortalNotFound` (a real 404 that offers "Back to
   my portal"), not a silent bounce to the dashboard.

`AppShell` repeats 1–3 in a `useEffect` and installs `installSessionGuards()` (bfcache /
focus re-check).

## 9. Which dashboard a role sees on `/workspace/app`

`workspace.app.index.tsx`:

1. `useEffect` — if the active role's home is not `/workspace/app`, redirect there
   (`replace: true`). Departments never sit on the manager's dashboard.
2. Otherwise the **active role** picks the component:
   `Transport Manager`/`Platform Admin` → `CentralDashboard`; `Fleet Operations` →
   `FleetManagerDashboard`; `Diesel` → `FuelManagerDashboard`; `Accounts` →
   `AccountantDashboard`; `Security` → `GateDashboard`; `HR` → `HRDashboard`;
   `Engineering` → `EngineerDashboard`; `Parts & Store` → `ProcurementDashboard`;
   anything else → `CentralDashboard`. All of them come from
   `src/components/fleetopsx/role-dashboards.tsx`.

## 10. Two more guards worth knowing

- **Notifications** are scoped by audience, not just by route: `notification-modules.ts`
  tags each module with the roles that may receive it, and the header badge / list read
  that. A role can open `/notifications` and still legitimately see nothing.
- **`workspace.app.unauthorized.tsx`** maps roles to their own home
  (`homeForRoles`), so "Return to Dashboard" never loops back into the page that just
  refused them.

## 11. Gaps and asymmetries in the code as it stands

These are real, read off the code — not opinions:

1. **`/workspace/app/fleet` and `/workspace/app/fleet-registry` guard in a `useEffect`**
   instead of `beforeLoad` (every other FO page uses `beforeLoad`). The page renders for a
   beat before the redirect fires.
2. **`/workspace/app/new-request` and `/workspace/app/password-request` have no role
   guard at all.** They are linked from the Transport Admin sidebar but any authenticated
   session can open them; only the server refuses the writes.
3. **Guard role lists are duplicated per file** (e.g. the same FO triple in five routes,
   the same eight lubricant roles in four). `hr-helpers` / `engineering-helpers` /
   `admin-departments` show the shared-constant pattern that the others do not follow.
4. **The role label spellings drift** (`Parts & Store` vs `Parts and Store`,
   `HR & Personnel` vs `HR and Personnel`, `Engineering & Maintenance` vs
   `Engineering and Maintenance`). The aliases exist to absorb this, but each new page has
   to remember to include them.

## 12. Adding a page (the checklist that keeps this coherent)

1. Create `src/routes/workspace.app.<name>.tsx`; the plugin regenerates
   `src/routeTree.gen.ts` (never edit it by hand).
2. Add a `beforeLoad` guard following the house pattern:

   ```tsx
   export const Route = createFileRoute("/workspace/app/<name>")({
     beforeLoad: () => {
       if (typeof window === "undefined") return; // live JWT is browser-only
       const allowed = ["Transport Manager", "Platform Admin"];
       if (!authService.getRoles().some((r: string) => allowed.includes(r))) {
         throw redirect({ to: "/workspace/app/unauthorized" });
       }
     },
     head: () => ({ meta: [{ title: "… | FleetOpsX" }] }),
     component: …,
   });
   ```
   Prefer a shared constant (`HR_ACCESS_ROLES`, `ENGINEERING_ACCESS_ROLES`) over a new
   inline list when the page belongs to an existing department.
3. If it is a department's **first** page, add the role → path entry to `role-home.ts`,
   otherwise that department's login lands on the manager's dashboard.
4. Add the nav item to **every** sidebar that should reach it — the sidebars are separate
   files under `src/components/fleetopsx/*-sidebar.tsx`, and `department-sidebar.tsx`
   holds HR / Engineering / Inventory / Parts / Accounts in one `DEPARTMENTS` map.
5. Gate capabilities (not access) with `active-role.ts` helpers rather than re-listing
   roles in the component.
6. `npx tsc --noEmit`, then exercise the route in the browser.
